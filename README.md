# Days to New Year

Небольшое приложение на Go, которое вычисляет количество календарных дней, оставшихся от заданной даты до ближайшего следующего Нового года (1 января следующего календарного года). Приложение доступно как HTTP-сервис и поддерживает проверку состояния и структурированное логирование.

Болотов Иннокентий

## Назначение

- Функция `daysToNextYear` — считает календарные дни до 1 января следующего года с учётом високосных лет и нормализации времени до начала дня.
- HTTP-сервис — предоставляет результат по запросу; дата может быть передана параметром, иначе используется текущая дата сервера.
- Health endpoint `/healthz` — для проверки работоспособности сервиса (Liveness/Readiness probe, мониторинг).
- Структурированные логи через `log/slog` — каждый HTTP-запрос логируется в JSON-формате.

## Требования

- Go **1.21** или новее (используются `log/slog`, `net/http`, `encoding/json`, `time`).
- ОС: Linux, macOS или Windows.
- Для запуска в контейнере — Docker 20.10+ (или совместимый).
- Для запуска CI — аккаунт GitHub (проверки выполняются через GitHub Actions).

Проверить установленную версию Go:

```bash
go version
```

## Сборка

Из корня репозитория:

```bash
go build ./...
```

Чтобы собрать исполняемый файл:

```bash
go build -o daysny .
```

После этого в текущей директории появится бинарник `daysny` (на Windows — `daysny.exe`).

## Запуск

### Локально

Запустить собранный бинарник:

```bash
./daysny
```

Или сразу через `go run`:

```bash
go run .
```

По умолчанию сервер слушает порт **8080**. При старте в лог уходит запись вида:

```json
{"time":"...","level":"INFO","msg":"server starting","addr":":8080"}
```

Собрать образ:

```bash
docker build -t daysny .
```

Запустить контейнер:

```bash
docker run --rm -p 8080:8080 daysny
```

Проверить:

```bash
curl "http://localhost:8080/healthz"
curl "http://localhost:8080/api/days?date=31-12-2023"
```

### Race detector

Проверка на гонки данных встроена в Go флагом `-race`:

```bash
go test -race ./...
```

> При использовании `-race` с покрытием обязателен `-covermode=atomic` — иначе `go test` завершится с ошибкой несовместимости флагов.

### Покрытие

Посчитать покрытие и посмотреть построчный отчёт:

```bash
go test -covermode=atomic -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

HTML-отчёт (откроется в браузере):

```bash
go tool cover -html=coverage.out
```

### Бенчмарки

Бенчмарк основной вычислительной функции:

```bash
go test -bench=. -benchmem -run=^$ ./...
```

Флаг `-run=^$` отключает обычные тесты, чтобы запускались только бенчмарки. Пример вывода:

```
BenchmarkDaysToNextYear-8   12345678   95.3 ns/op   0 B/op   0 allocs/op
```

Ключевой показатель — `0 allocs/op`: функция не должна выделять память при расчёте.

## HTTP API

### `GET /api/days`

Возвращает количество календарных дней до ближайшего следующего Нового года.

**Параметры запроса**

| Параметр | Обязательный | Формат         | Описание                                                        |
|----------|--------------|----------------|-----------------------------------------------------------------|
| `date`   | нет          | `ДД-ММ-ГГГГ`   | Дата, от которой считается остаток. Если не указана — берётся текущая дата сервера. |

**Примеры запросов**

Текущая дата:

```bash
curl "http://localhost:8080/api/days"
```

Конкретная дата:

```bash
curl "http://localhost:8080/api/days?date=31-12-2023"
```

**Успешный ответ** — `200 OK`, `Content-Type: application/json; charset=utf-8`:

```json
{"days_left":1}
```

**Ошибка валидации** — `400 Bad Request`:

```json
{"error":"Неверный формат даты. Используйте ДД-ММ-ГГГГ"}
```

**Неподдерживаемый метод** — `405 Method Not Allowed`:

```json
{"error":"Разрешен только метод GET"}
```

### `GET /healthz`

Проверка состояния сервиса. Возвращает `200 OK` и JSON с полем `status`.

Формат ответа выбран так:

- **JSON** — согласуется с остальным API, клиентам не нужно уметь разбирать другой формат.
- **`{"status":"ok"}`** — короткий машиночитаемый ответ, удобный для мониторинга и Kubernetes-probe.
- **200 vs 503** — если сервис живой, возвращается 200; если не готов принимать трафик (например, не поднялись зависимости) — 503. Сейчас внешних зависимостей нет, поэтому всегда 200, но контракт заложен на будущее.

**Пример запроса**

```bash
curl "http://localhost:8080/healthz"
```

**Успешный ответ** — `200 OK`:

```json
{"status":"ok"}
```

**Неподдерживаемый метод** — `405 Method Not Allowed`:

```json
{"error":"Разрешен только метод GET"}
```

### Формат ответа

Успешный расчёт (`GET /api/days`):

| Поле        | Тип   | Описание                          |
|-------------|-------|-----------------------------------|
| `days_left` | int   | Количество календарных дней (≥ 0) |

Проверка состояния (`GET /healthz`):

| Поле     | Тип    | Описание                       |
|----------|--------|--------------------------------|
| `status` | string | `"ok"` — сервис работоспособен |

Ошибка:

| Поле    | Тип    | Описание              |
|---------|--------|-----------------------|
| `error` | string | Текст сообщения об ошибке |

## Соответствие status code

| Код | Когда возвращается                                  |
|-----|-----------------------------------------------------|
| 200 | Успешный расчёт или успешная проверка `/healthz`    |
| 400 | Некорректный формат `date`                          |
| 405 | Использован HTTP-метод, отличный от `GET`           |

## Логирование

Каждый HTTP-запрос проходит через middleware, который логирует:

- HTTP-метод;
- путь и query-строку;
- фактически возвращённый статус;
- длительность обработки в миллисекундах;
- удалённый адрес клиента.

Формат — структурированный JSON (`log/slog` со `slog.NewJSONHandler`). Пример записи:

```json
{"time":"2024-12-31T14:30:00.123Z","level":"INFO","msg":"http request",
 "method":"GET","path":"/api/days","query":"date=31-12-2023",
 "status":200,"duration_ms":0,"remote":"127.0.0.1:54321"}
```

Такие логи легко парсятся системами вроде Loki, ELK или CloudWatch без regexp.

## Continuous Integration

Workflow описан в `.github/workflows/ci.yml` и запускается:

- при push в `main` / `master`;
- при открытии/обновлении Pull Request в эти же ветки.

В рамках CI выполняются:

- `gofmt -l .` — проверка форматирования;
- `go vet ./...` — статический анализ;
- `go mod tidy` (с проверкой отсутствия диффа) и `go mod verify` — корректность зависимостей;
- `govulncheck` — проверка зависимостей на известные уязвимости;
- `go build ./...` — сборка;
- `go test -race -covermode=atomic -coverprofile=coverage.out ./...` — тесты с детектором гонок и покрытием;
- проверка порога покрытия (не ниже 70%);
- загрузка артефакта `coverage.out` для разбора.

## Зависимости

Проект использует только стандартную библиотеку Go. Внешних модулей нет, поэтому `go.sum` может отсутствовать. Все проверки зависимостей (`go mod tidy`, `go mod verify`) всё равно выполняются в CI и защищают от случайного добавления неиспользуемых или повреждённых модулей.
